# Oculus course directory

This file describes a course folder in an Oculus library — one University of
Melbourne subject, synced from Canvas, Ed Discussion and Echo360. The folder
is named for the subject: `COMP30026_2026_SM2` is COMP30026, semester 2, 2026.
`syllabus.md` and `home.md` name it in full. If you are reading this from the
library's own `agents/` folder instead — where the in-app chat runs you —
the course folders are at `../courses/<CODE>/`, and everything below is about
them.

Oculus fills this folder by syncing Canvas, Ed Discussion and Echo360 from the
desktop app. Only `uploads/` and `documents/` are the student's own.

```
./
  syllabus.md      home.md
  announcements/   Canvas announcements, one .md each
  assignments/     briefs and due dates, one .md each
  ed/              Ed Discussion threads, NNNN-slug.md
  files/           downloads plus parsed siblings:
                     13.pdf  13.md  13.pages.json  13_images/
  modules/         module pages, in course order
  pages/           Canvas pages
  quizzes/         worksheets and quizzes
  images/          images referenced by the markdown above
  uploads/         the student's own files, added by hand
  documents/       the student's own notes, written in the app — markdown
                   you may read; they are the student's to write
  agents/          yours: INSTRUCTIONS.md, and memories/ linked to the
                   library's store (see Memory)
```

Per-page PDF text is **not** on disk — it lives in the Oculus database. Plain
`grep`/`rg` over this folder silently misses every slide deck; `oculus grep`
reads both halves.

## Rules

- Write only inside `agents/`. Everything else here is regenerated by sync
  or is the student's own, so edits elsewhere are both off-limits and lost.
- Keep memories as markdown in the library's memory store, not `.claude/` and
  not `.codex/`, so every agent that works here shares one. See Memory below:
  it lives under the library's own `agents/` because the in-app chat runs
  sandboxed and that is the only folder it can write to.
- Never touch `oculus.db` directly. The CLI is the door in both directions:
  `oculus search|grep|read|files|calendar` read it, and `oculus project` /
  `oculus task` write the student's plan into it — the same rows the app draws
  its board from, so a task you add appears there, on a board or in the Tasks
  view if it is filed nowhere.

## Memory

Nothing carries from one session to the next except what is written here, so
read it at the start and write to it as you go. **`oculus memory` is the way
in and out** — it writes the file, the front matter and the dates, and
rewrites that folder's `MEMORY.md` from the files beside it, so an entry
cannot go missing from the index and there is no second write to remember.

```bash
oculus memory list -s <CODE>            # what is already known about this subject
oculus memory read tchan-study-workflow # one of them in full
oculus memory write "the-name" --type reference --about "the line the index shows" --text "the fact" -s <CODE>
oculus memory rm the-name               # it turned out wrong; no undo
oculus memory move the-name -s <CODE>   # it was filed in the wrong bucket
```

**Write the moment something is true**, not in a sweep at the end of a session
that never comes: I said something about myself or my plan that the library
does not record; you worked out something that cost real effort; I corrected
you; a due date or a scope moved.

**Filing is the `-s` flag.** With it, the fact goes in that subject's bucket —
anything that names one subject does, including when it came up while working
on something else. Without it, the cross-subject bucket: facts about me, and
what holds across subjects. A `feedback` or `project` memory also wants
`--why` and `--how`, because an instruction a later session cannot act on is
not worth keeping. Passing a name that is already filed updates it in place,
which is what makes this a store of what is true rather than a log.

Standing preferences are the exception: they live in `../../agents/TASTE.md`,
one bullet under `Writing`, `Working` or `Study`, and that file says when
something has earned a line there. `oculus memory promote <name> --section
working` is the move from a `feedback` memory to a bullet.

The buckets are real folders under the library's own `agents/` — the only
place the in-app chat can write — and this course folder's `agents/memories/`
is a symlink to its one. The command takes `-s` and finds them, so neither
path has to be typed.

`TASTE.md` and the cross-subject index are opened at the top of every in-app
conversation, so keep them short.

## Tools

Bash, `grep`, `find` and other read-only tools are fine. The `oculus` CLI is
the better door for anything indexed — if it is not on `PATH`, ask me to
install it (`bun run cli:install` in the Oculus repo) rather than working
around it.

```bash
oculus search "kkt conditions" -s COMP30026 -n 8  # rank pages by meaning
oculus grep "sprint retrospective" -s COMP30026   # regex over markdown AND pdf pages
oculus read 13.pdf --pages 30-35                  # parsed page markdown
oculus files COMP30026 --type pdf                 # what is there to read
oculus calendar COMP30026 -d 14                   # classes and due dates
oculus project list -s COMP30026                  # what is planned, and how far along
oculus task add -p 3 --batch -                    # a whole breakdown in one call
oculus task add "email the tutor"                 # no -p: filed nowhere, for now
oculus task list                                  # every task, unfiled ones first
oculus task refile 12 -p 3                        # file it, subtasks and all
oculus memory list -s COMP30026                   # what is already known
oculus memory write --type reference --about "…" --text "…" -s COMP30026
```

**Run one command per call.** The shell these commands go to refuses a
compound invocation, and a refusal is final — there is nobody to approve it and
the turn carries on without the answer. So:

- **No loops and no substitution.** `for f in …`, `while`, `$(…)` and backticks
  are all refused. Five files means five calls, which is cheaper than one
  refusal.
- **No shell variables.** `$CODE`, `$f`, `${x}` — write the value out. The
  subject code is eight characters; expanding it saves nothing and costs the
  command.
- **No newline inside an argument.** A long `--brief` or task title is one
  line. If it genuinely needs paragraphs, write the file first and pass the
  path.
- Pipes and `&&` are fine, and so is `| head`. It is the loops, the variables
  and the multi-line arguments that fail.
- `oculus` is already on `PATH`. Call it by name, never by an absolute path,
  and do not `cd` out of this folder to reach it.

Planning is a write, so it has its own rules. A project's board names its own
columns (`oculus project show <ID>` prints their ids), and a breakdown goes in
as one `--batch` JSON array rather than one command per task —
`oculus task add --help` is the contract. A task **need not belong to a
project**: `oculus task add` with no `-p` writes an *unfiled* task, which is
what to reach for when something has to be written down before anyone has
decided where it goes. `oculus task refile` files it later and takes its
subtasks with it. Do not invent an "Inbox" project for this; there is nothing
to clean up if an unfiled task is never filed.

Pass this folder's own subject code to `-s`: the CLI has no notion of the
working directory, so without it you get the whole library back. `search`
embeds the query through the embedding provider configured in the app, so it
needs that key to be set; when it can't run it fails loudly and points at
`grep`. Add `--json` to any command for machine-readable output.
